# V3.3 — Direction-aware overcurrent lockout

Status: **implemented, awaiting owner hardware sign-off.** Extends the V3.2
direction-aware lockout ([v3.2-direction-aware-lockout.md](v3.2-direction-aware-lockout.md))
to over-current, which that work explicitly deferred: "Over-current is not
tracked as a distinct flag in this project... noted for a future task."

## Investigation — is direction actually available?

Yes, directly, with no inference needed. `bms/protocol.h`'s `TB_ALRMS` enum
(the BMS 0x44 alarm-info bitmap) already carries these as **separate bits**:

```
CHARGE_OVER_CURRENT_PROTECT       = 1ULL << 2
DISCHARGE_OVER_CURRENT1_PROTECT   = 1ULL << 4
DISCHARGE_OVER_CURRENT2_PROTECT   = 1ULL << 56   // out of scope, see below
```

Both bit 2 and bit 4 were already part of `filters::CRITICAL_ALARM_MASK`
(carried over unchanged from V2.67's `TB_CRITICAL_ALARM_MASK`) — the BMS has
always reported these distinctly. The gap was purely in **routing**:
`runSafety.cpp`'s crit-bit classifier only recognized `UV_ALARM_BITS`
specially; everything else, including both OC bits, fell into the generic
`alarm_flags 0x40` "BMS critical" bucket, which blocks both directions.

Per the Topband datasheet, charge and discharge overcurrent protection are
separately specified parameters (~32±5 A / ~33±5 A, ~6±1 s delay). The gateway
does not need to know these exact thresholds or re-derive them from raw
current — it only needs to react correctly to the BMS's own pre-computed
alarm bit, exactly as it already does for over-voltage and under-voltage.

**Not in scope:** `DISCHARGE_OVER_CURRENT2_PROTECT` (bit 56) — a second
discharge-OC protection stage — was never part of V2.67's critical mask and
still isn't. Adding it would be new alarm detection, not a direction-aware
routing fix of an existing one; flagged here for a possible future task, not
acted on.

## Fix

`safety/filters.h` gets two new bit masks (`OC_CHARGE_ALARM_BITS` = bit 2,
`OC_DISCHARGE_ALARM_BITS` = bit 4), and `runSafety.cpp`'s crit-bit classifier
changes from an if/else chain (first match wins) to independent checks, since
a single 0x44 response can combine multiple critical bits (e.g. UV and
charge-OC on the same pack) — the old if/else would silently drop the second
condition.

New `alarm_flags` bits (0x01 and 0x04 were unused in V2.67 — confirmed against
`test/host/fixtures/v267/v267_reference.py`, which only assigns
0x02/0x08/0x10/0x20/0x40/0x80):

```
0x01 = charge over-current    (V3.3; new)
0x04 = discharge over-current (V3.3; new)
```

`block_charge` / `block_discharge` extended:

```
block_charge    = (alarm_flags & 0x02) || (alarm_flags & 0x01) || (factor_charge == 0)    || (alarm_flags & 0x40)
block_discharge = (alarm_flags & 0x10) || (alarm_flags & 0x04) || (factor_discharge == 0) || (alarm_flags & 0x40)
```

Same conservative principle as the OV/UV fix: everything left in the 0x44
bitmap after UV/charge-OC/discharge-OC classification (OV bits, temp bits,
short-circuit, reserved bits) still falls into 0x40 and blocks both.

## CAN encoding — natural consequence, not a new decision

Both bits chosen (0x01, 0x04) were already "spoken for" by existing but
previously-dead code, which is a strong confirmation they were the intended
slots:

- **Pylontech 0x359**: byte0 bit7 (discharge over-current) and byte1 bit0
  (charge over-current) are *standard Pylontech LV protocol bits* that were
  already documented in `pylontech.cpp`'s byte-layout comment and covered by
  regression tests asserting they stay at 0 ("charge over-current not
  fabricated") — because nothing ever set them. They now wire directly to
  `alarm_flags & 0x01` / `& 0x04`. The old "never fabricated from CCL/DCL"
  tests are unaffected (they use `alarm_flags` values without the new bits);
  two new paired tests added confirming the real wiring.
- **Victron 0x35A / SMA 0x35A**: both already had `if (af & 0x01) out[4] |= 0x80;`
  (high-priority alarm) as a dormant V2.67-derived mapping — bit 0x01 was
  wired in the CAN encoder before anything in `runSafety.cpp` ever set it.
  Discharge-OC (0x04) has no dedicated Victron/SMA bit slot (same situation
  UV/OV/temp don't share), so it folds into the same shared high-priority-alarm
  bit, added alongside the existing 0x01/0x40 checks.

CCL/DCL themselves need no encoder changes: `ccl_amps`/`dcl_amps` already flow
from `block_charge`/`block_discharge` regardless of which alarm bit caused the
block, so 0x351 (Pylontech/Victron/SMA current limits) and 0x35C (Pylontech
enable bits) were already correct the moment `runSafety.cpp` was fixed.

## Test coverage

`test_safety.cpp` `[lock]`:
- `lock: charge over-current (0x01) → blocks CHARGE only` — CCL 0, DCL stays
  `count × 30 A`, not folded into 0x40.
- `lock: discharge over-current (0x04) → blocks DISCHARGE only` — DCL 0, CCL
  stays `count × 30 A`, not folded into 0x40.
- `lock: charge-OC and under-voltage combined on one pack → both classified
  independently` — regression for the if/else → independent-classification
  rewrite; both bits must be set, neither swallows the other.
- `lock: BMS critical alarm (0x40) → blocks BOTH (non-directional)` — updated
  to use bit 11 (`SHORT_CIRCUIT_PROTECT`) instead of bit 4, since bit 4 is now
  direction-aware and no longer a valid example of "generic non-directional
  critical."

CAN encoder tests added: Pylontech 0x359 (charge-OC → byte1 bit0, discharge-OC
→ byte0 bit7, each independently, neither bit fabricated by the other),
Victron/SMA 0x35A (0x04 joins 0x01/0x40 in the high-priority-alarm mapping).

All 22 pre-existing `[!shouldfail]`-tagged tests (from the CI-real-tests task)
were re-run after this fix: none flipped to passing (checked individually,
not just via the aggregate ctest exit code) — this fix does not touch
`dcl_amps`/`factor_*`/`event_count` in the ways those tests diverge on, so
their root cause remains open and unrelated to over-current.

## Version

that happens only at release-prep ("release: bump version to X") commits.
