# V3.2 — Direction-aware safety lockout

Status: **implemented, awaiting owner hardware sign-off.** Replaces V2.67's blanket
"lock both directions to zero" with a per-direction protection lock in
`src/safety/runSafety.cpp`. No CAN encoding change (already audited correct in
[v3.2-pylontech-conformance-audit.md](v3.2-pylontech-conformance-audit.md)); the
enable bits and current limits now naturally reflect the direction-aware CCL/DCL.

## Audit — every condition feeding the lock, its correct direction

| Condition | Source flag | Before (V2.67) | Correct | Fixed? |
|---|---|---|---|---|
| Cell/pack over-voltage | `alarm_flags 0x02` | both | **charge only** (discharge lowers V) | yes |
| Cell/pack under-voltage | `alarm_flags 0x10` | both | **discharge only** (charge raises V) | yes |
| Charge over-temperature | `factor_charge == 0` (t > charge_temp_max) | charge only¹ | charge only | already correct² |
| Discharge over-temperature | `factor_discharge == 0` (t > discharge_temp_max) | discharge only¹ | discharge only | already correct² |
| Charge low-temperature (cold) | `factor_charge == 0` (t < charge_temp_min) | charge only¹ | charge only (LiFePO4 plating) | already correct² |
| (No discharge low-temp exists in the Topband spec — discharging cold is fine) | — | — | discharge unaffected | n/a |
| Over-current charge / discharge | folded into `alarm_flags 0x40` | both | not separately decoded → kept **both** (conservative) | no (see ³) |
| BMS-reported critical alarm (0x44) | `alarm_flags 0x40` | both | **both** (non-directional) | kept both |
| No packs online | `alarm_flags 0x80` | both | **both** (no data) | kept both |
| SoC ≥ 100 % taper | (not a fault) | charge 0 | charge 0, **not a lockout** | clarified |

¹ Temperature was ALREADY direction-separated in V2.67: `factor_charge` uses the
charge temperature window and `factor_discharge` the discharge window, each applied
only to its own limit. The blanket lock at `runSafety.cpp:442-448` never touched
temperature — only OV/UV/BMS. So the temperature directions needed no logic change.

² Change made for temperature: the `factor == 0` cutoffs are now folded into the
same post-taper block set. This fixes a latent bug — at SoC ≥ 99 % the SoC taper
set `safe_chg = count × 2 A`, which previously **overrode** a cold-charge cutoff,
letting the gateway request a 2 A trickle into a pack too cold to charge (LiFePO4
plating risk). Applying the block after the taper makes the cutoff authoritative.
Regression test: `lockdir: cold charge-cutoff at 99% SoC → charge stays 0`.

³ Over-current is not tracked as a distinct flag in this project — the BMS 0x44
bitmap's OC bits are classified into the generic `0x40` "critical" bucket. Per the
conservative invariant ("anything not fully confident stays both-directions"), a
BMS-reported critical alarm keeps blocking both. Decoding OC per-direction would
require extending the 0x44 classifier and is out of scope here; noted for a future
task.

## Refactored mechanism

Two booleans computed from the already-populated `alarm_flags` / `factor_*`:

```
block_charge    = (alarm_flags & 0x02) || (factor_charge == 0)    || (alarm_flags & 0x40)
block_discharge = (alarm_flags & 0x10) || (factor_discharge == 0) || (alarm_flags & 0x40)
```

Applied AFTER the SoC taper, immediately before `out.ccl_amps` / `out.dcl_amps` are
assigned, so a genuine protection stop is authoritative and the near-full taper can
never re-open a trickle. `lockout_flags` (0x01 charge, 0x02 discharge) records which
direction was disabled *by protection* (never by the taper) for the UI/alert layer.
The "no packs online" branch sets `lockout_flags = 0x03` directly.

`SafetyState::lockout_flags` is one byte placed in the struct's existing tail
padding (alongside `temp_alarm`) → net-zero internal DRAM (verified: 44792 B before
and after).

## Paired test coverage (`[lockdir]` + updated `[lock]`, all passing)

Each row verifies BOTH the blocked direction AND the direction that must stay live:

- baseline healthy → both full, `lockout_flags == 0`
- cell over-voltage → CCL 0, **DCL full**, lockout 0x01 only
- charge over-temperature (55 °C) → CCL 0, **DCL full**, lockout 0x01, temp_alarm hot
- discharge over-temperature (isolated cfg) → DCL 0, **CCL full**, lockout 0x02 only
- charge low-temperature (0 °C) → CCL 0, **DCL full**, lockout 0x01, temp_alarm cold
- cold cutoff at 99 % SoC → CCL stays 0 (not the 2 A taper trickle) — regression
- SoC 100 % taper → CCL 0 but `lockout_flags == 0` (battery full ≠ fault)
- no packs online → both 0, lockout 0x03
- combination OV(pack0) + UV(pack1) → both 0, lockout 0x03, neither masks the other
- updated `[lock]` OV/UV/BMS cases assert the new direction split (Manual mode so the
  surviving direction carries its real `count × 30 A`, not a coincidental 0)

## Visibility

- Dashboard **Runtime Estimate** card shows a red banner "Discharge disabled:
  \<reason\>" when `lockout_flags & 0x02`; **Battery Power** card shows a lighter
  amber "Charge disabled: \<reason\>" when `lockout_flags & 0x01`.
- Alert log (`diag::alerts::emit`) gets a Warn entry when a direction lock engages
  ("Charge/Discharge disabled: \<reason\>") and an Info entry when it clears, edge-
  detected in `poller.cpp` — so the history shows, e.g., over-voltage disabling
  charge only while discharge stayed available.

## Note on the Deye 0x359 over-voltage bit

The 0x359 over-voltage protection bit is still set while a cell is over-voltage
(unchanged, correct). The gateway now permits discharge (DCL > 0, discharge-enable
Yes), which lets the pack self-correct. If a specific inverter additionally gates
discharge on the 0x359 alarm bit itself, that is inverter-side behaviour; the
gateway's job — permit the physically-correct direction — is now done correctly.
