# V3.2 research: SmartShunt as a SoC source — design options

**Status:** research only, no implementation. Feeds a follow-up implementation prompt once the owner picks a direction.

---

## 0. Important finding before anything else: this is partly already built

The bus/source layer for exactly this fusion problem already exists in `src/sources/`, and it already
solves the **current** version of this problem. It does not yet solve the **SoC** version, and the two
places that talk about SoC fusion currently disagree with each other:

- `src/sources/aggregator.cpp:6-9` defines `SHUNT_LEAD_THRESHOLD_A = 0.5f` and uses it to hand over
  **current** reporting from BMS to shunt below 0.5 A (`aggregator.cpp:53-58`). This is the exact
  hard-cutover pattern the owner is worried about, already shipped, already for current. It has not
  caused a reported problem yet because current is instantaneous (a step change in an amps reading is
  much less visually jarring than a step change in a percentage that the user tracks over hours).
- `src/sources/source.h:28` defines `Metric::SHUNT_SOC` with a comment: *"shunt-counted SOC (%),
  supplementary only — never overrides BMS SOC."* `aggregator.cpp:73-76` implements exactly that: SoC
  fusion is a no-op passthrough, wired only to the diagnostics page (`src/web/handlers_diag.cpp:387`,
  field `soc_pct`). It is not blended into `soc_avg`, not published over MQTT, not used by CAN TX.
- `docs/ROADMAP.md:290-292` says the opposite: *"SOC: SmartShunt (if online) > BMS reported"* — shunt
  should **win** outright once online.
- `src/storage/config.h:94-96` has a dormant `Config::SocMode { Calculated, RawBms, Hybrid }` field.
  It round-trips through config load/save/JSON but nothing in `runSafety.cpp` or elsewhere branches on
  it — it reads like a reserved hook for exactly this feature, never wired up.

So the real starting question for the owner is not "should we build fusion" — it's "which of these two
already-written statements of intent (`source.h`'s 'never override' vs `ROADMAP.md`'s 'shunt wins') is
still correct," plus whether `Config::SocMode` is the intended home for the selector. Section 5 comes
back to this.

## 1. What data is actually available

### From the BMS (per pack, via RS485)

- `src/bms/protocol.h:112` — `uint8_t soc` per pack, parsed straight from the BMS analog frame
  (`src/bms/protocol.cpp:290-292`), copied through unmodified into `BmsPackSnapshot`
  (`src/bms/snapshot.cpp:29`). No smoothing, no local Coulomb-counting on the gateway side — this is
  whatever the BMS's own firmware computed.
- `src/bms/protocol.h:107` — `float pack_current` per pack, signed, `+` = charge, scaled from a raw
  int by 0.01 A (`src/bms/protocol.cpp:260`).
- **Two independent low-current quirks already documented in code, not one:**
  1. **Sample-gap quirk** (`src/bms/snapshot.cpp:7-9`, referencing architecture §5.3 / V2.66 finding H1):
     the BMS firmware reports `current = 0` for ~90 second windows between real samples — a reporting
     *gap*, not a measurement floor. The gateway papers over this today with a 120 s hold-last-value
     window on `pack_current` (`CURRENT_HOLD_MS`, threshold `fabsf(current) > 0.01f`).
  2. **Coulomb-counter dead zone** (`src/sources/aggregator.cpp:6-9`): below ~0.5 A the BMS's own
     Coulomb counter "loses accuracy and may report 0." This is the threshold the owner's prompt is
     about. It is a measurement-floor problem, not a reporting-cadence problem, and it plausibly
     degrades the BMS's own SoC integration during any extended low-current period (float/absorption
     tail, light overnight load), not just the reported current value.
  - The BMS's actual SoC algorithm is opaque (no protocol doc for it beyond the raw field), so we can
    observe the symptom (SoC reading stalls or drifts when current is near-zero for a long stretch) but
    can't reason about its internals.

### From the SmartShunt (once BLE integration exists — assumed available for this research)

- Total bank current, 1 Hz, accurate across its full rated range including near-zero (that is the
  point of a shunt: it measures a voltage drop across a known resistance, with no coulomb-counting
  dead zone the way a BMS's cheaper current sensing might have).
- Victron shunts run their own Coulomb counter for SoC, with periodic **synchronization** to 100% when
  the shunt observes a "tail current" condition consistent with a full-charge event (this is standard
  Victron SmartShunt/BMV behavior — periodic resync anchors the integrator, so shunt SoC does not drift
  unbounded over time the way a naive integrator would).
- Already plumbed in as `Metric::SHUNT_SOC` (`src/sources/source.h:28`), fed by `ShuntSource`
  (`src/sources/shunt_source.h/.cpp`), decoded from Victron Instant Readout BLE records
  (`src/sources/ble_scanner.cpp:323-364`), and exposed today only on the diagnostics page.

### The core asymmetry: bank-level vs. per-pack

- Shunt SoC is **one number for the whole bank** — it cannot see individual packs, only the sum of
  currents in/out of the parallel bank as if it were one battery.
- BMS SoC is **N numbers**, one per pack, and packs are known to diverge from each other over time via
  ordinary Coulomb-counter drift (per-pack current sensing error, temperature differences, connector
  resistance differences causing slightly different effective currents per pack in a parallel bank).
  These are not the same quantity, and no algebraic operation on the BMS per-pack values recovers
  exactly what the shunt measures unless the packs are perfectly balanced (they are not, that is the
  whole reason a Cell Drift feature already exists for cell voltages, `src/app/drift_ring.cpp`,
  `docs/architecture.md:1869-1871`, though for cell *voltage* drift, not SoC drift — see note in
  section 2).
- Today's "bank-level SoC" is not even the shunt's measurement — it's `soc_avg`, the arithmetic mean of
  per-pack BMS SoC values (`src/safety/runSafety.cpp:276,289`: `sum_soc += p.soc` then
  `soc_avg = sum_soc / count`). This average is **not just a display value** — it already feeds the
  charge taper logic at 99%/100% thresholds (`runSafety.cpp:432-436`), so any change to what "the" SoC
  means has a safety-adjacent blast radius, not just a UI one.

**Note on "SoC drift between packs":** the research prompt and project memory both refer to this as if
it were already documented. It is not — every existing "drift" feature and doc reference
(`docs/architecture.md:752`, the Cell Drift chart metric, `CHANGELOG.md`'s "Battery Drift Details") is
about per-cell *voltage* drift within a single pack, not SoC/Coulomb-counter drift between packs across
the bank. Inter-pack SoC divergence is a reasonable inference (packs in parallel with independent
Coulomb counters will drift from each other over enough cycles) but is currently un-instrumented and
unverified in this codebase. Flagging this because option 4 below assumes it happens; it should be
treated as a hypothesis to confirm with real pack data, not an established fact.

## 2. Why a hard 0.5 A cutover risks a visible SoC jump — confirmed, with a worked example

The owner's concern is correct, and it is a strictly bigger problem for SoC than the current-fusion
cutover already shipped in `aggregator.cpp`, for one structural reason: **current is stateless, SoC is
stateful.**

When `TOTAL_CURRENT` flips source at 0.5 A, the displayed number changes but it doesn't accumulate —
next cycle it can flip back with no lingering effect. SoC is different: it's an integral, and more
importantly it's a number the user watches trend over hours (`72% ... 71% ... 70%`), so any
non-monotonic jump is immediately visible as "wrong," whereas a momentary current-reading blip is easy
to dismiss as noise.

**Worked example**, using the owner's own numbers: bank at 44% by BMS average, shunt independently at
42% (a 2-point gap that is entirely plausible — different zero points from the last resync, different
integrated error since then). Load is easing off, current crosses 0.5 A downward.

| Time | Current | Active source (hard cutover) | Displayed SoC |
|---|---|---|---|
| t0 | 0.6 A | BMS | 44% |
| t1 | 0.5 A | BMS (boundary, inclusive) | 44% |
| t2 | 0.49 A | **shunt** | **42%** |
| t3 | 0.3 A | shunt | 42% |

At t1→t2 the dashboard shows SoC *dropping* 2 points in one polling interval while the battery is
sitting nearly idle at a light load. To a user watching a runtime/SoC graph this reads as either a
gateway bug or an alarming discharge event, neither of which is true. Two things make it worse than a
generic "two sensors disagree" problem:

1. **It's not random noise, it's a step function tied to a threshold the user never sees.** The same
   2-point gap that was invisible while current sat comfortably above 0.5 A becomes visible on exactly
   the cycle it crosses the line. Any threshold, however placed, produces this same discontinuity
   *somewhere* — it doesn't have to be a "bad" threshold value.
2. **Current dithers around thresholds constantly at low load** (compressor cycles, WiFi radio bursts,
   inverter standby draw ticking). If current oscillates 0.4 A / 0.6 A / 0.4 A near the boundary, the
   hard cutover would make the displayed SoC oscillate 42% / 44% / 42% every poll cycle — an obviously
   broken-looking readout, not a one-time jump. This is materially worse than the single-jump case in
   the table above and is the likely real-world failure mode, not an edge case.

So: confirmed, not just as a theoretical risk but as a near-certain outcome under normal light-load
behavior (evenings, float charge, small parasitic loads), and confirmed to be worse for SoC than it is
for the current-value cutover already shipped, precisely because SoC is trended and current is not.

## 3. Architecture options

### Option A — Hard cutover (baseline, for comparison only)

Below 0.5 A show shunt SoC as "the" SoC, above it show BMS `soc_avg`. This is the pattern
`aggregator.cpp` already uses for current, applied naively to `SHUNT_SOC`.

- **What's shown:** whichever source is "active" this cycle, single number.
- **Transition:** step discontinuity exactly as demonstrated in section 2, plus oscillation risk if
  current dithers near 0.5 A.
- **Honest downside:** this is the one option that reliably produces a user-visible correctness
  complaint. Including it only as the thing to *not* build, per the owner's own instinct.

### Option B — Weighted blend across a current band (e.g. 0.3-0.7 A)

Instead of switching exactly at 0.5 A, linearly blend `soc_display = w * shunt_soc + (1-w) * bms_soc`
where `w` ramps 0→1 as `|current|` moves from the top of the band down to the bottom (matching the
"BMS leads at high current, shunt leads at low current" direction already established for
`TOTAL_CURRENT`).

- **What's shown:** a blended number, single value, source-agnostic to the user.
- **Transition:** smoothed in *current-space* — no instant jump at a single amp value.
- **Does it actually fix the problem, or just spread it out?** Spreads it out, does not fix the root
  cause. If shunt and BMS disagree by 2 points and stay disconnected once fully into shunt territory
  (say current drops to 0.1 A and stays there for an hour), the displayed value still ends up equal to
  raw shunt SoC — spread over a wider current range doesn't change the destination, only the slope of
  getting there. It also introduces a **new** failure mode: if current dithers *within* the 0.3-0.7 A
  band (very plausible, see section 2), the blend weight `w` recomputes every cycle and the *blended*
  SoC will visibly wobble between the two sources' values even though neither underlying value changed
  — this can look worse than a single clean jump, because now it looks like noisy jitter rather than
  one legible event.
- **Honest downside:** more code, more state (band edges become new magic numbers to justify and
  tune), and the disagreement between sources is real and doesn't go away — it's just diluted across a
  wider window rather than fixed. Worth building only if the owner values "no instant jump" over "no
  persistent wobble," which is a real trade-off, not a strict improvement.

### Option C — Shunt as always-on primary bank SoC, BMS as fallback only

If the shunt is confirmed accurate across its *entire* rated current range (not just at low current,
which is its whole selling point relative to the BMS), then there is no reason to ever switch sources
based on current level at all. Use shunt SoC as "the" bank SoC whenever the shunt is present and its
data is fresh; fall back to `soc_avg` only when the shunt is absent, disabled, or stale
(`ReadingStatus::Stale`/`Unavailable`, already modeled in `src/sources/source.h:33-37`).

- **What's shown:** bank SoC = shunt reading, full stop, whenever shunt is online. No current-based
  branching, no band, no threshold to tune.
- **Transition:** the only transition is shunt-online ↔ shunt-offline (BLE connect/disconnect), which
  is a rare, discrete, and honestly-labelable event ("shunt disconnected, falling back to BMS
  estimate") rather than a constant micro-threshold the user never sees. This is a fundamentally
  different, better kind of transition to expose in the UI than a current-crossing.
- **Is shunt accuracy at high current good enough?** This is the crux assumption and it's a
  hardware/sensor-class claim, not something derivable from this codebase — a resistive shunt with a
  Coulomb counter is generally accurate across its full rated range (that's the point of the sensor
  class), but the actual SmartShunt's calibration, resync cadence, and behavior under the specific
  charge/discharge profile of this system are unverified here since the BLE integration doesn't exist
  yet. This needs to be validated empirically once hardware is in hand (log shunt SoC vs. BMS `soc_avg`
  side by side across full cycles before trusting shunt-primary) rather than assumed from the sales
  pitch.
- **Honest downside:** if that assumption is wrong — e.g. the shunt's own resync logic misfires, or
  there's a Victron-side firmware quirk, or the shunt's SoC is only as good as its user-configured
  battery capacity/Peukert settings which may not match this pack's true capacity — then *all* SoC
  display quality now depends on one device instead of two, and there's no cutover threshold left to
  fall back to (only presence/absence). It also throws away the entire premise of "BMS leads, shunt
  fills the low-current gap" that the existing `aggregator.cpp` current-fusion logic and `ROADMAP.md`
  motivation both describe — this is the simplest option precisely because it's the most aggressive
  reversal of the current design's stated philosophy ("BMS role shrinks to cell voltages + temps +
  alarms only," `docs/ROADMAP.md:285`, which is explicitly the eventual direction ROADMAP.md already
  wants).

### Option D — BMS-primary with shunt-driven resync (correction model)

Keep per-pack BMS SoC as the value that's always displayed and always feeds safety/charge-taper logic
(preserving `soc_avg`'s existing role in `runSafety.cpp:432-436` untouched). Instead of ever *replacing*
the displayed number with the shunt's, use the shunt's low-current-accurate Coulomb counting to
periodically **correct** the aggregate the BMS values are derived from — conceptually similar to how the
Victron shunt itself uses tail-current detection to resync to 100% rather than trusting its integrator
forever.

Concretely: when current has been below the BMS dead zone for some minimum dwell time (long enough that
the BMS's own SoC is known-stale/unreliable, not just momentarily below 0.5 A), take the shunt's
delta-SoC (or delta-Ah) over that same window as the more trustworthy estimate of what actually changed,
and apply that correction as a slow bias/offset nudge to the displayed aggregate rather than a
value swap — no discontinuity because nothing is ever swapped, only nudged, and the nudge only fires
during periods where the corrected value and the pre-correction value are close anyway (low current =
small nudge magnitude by construction, since not much charge moved during the correction window).

- **What's shown:** still `soc_avg`-derived, still per-pack values fully intact and BMS-sourced;
  the aggregate gets progressively more accurate over time via low-current resync events, but the user
  never sees a source label change.
- **Transition:** none, by design — this is the option built specifically to avoid the section 2
  problem rather than mitigate it.
- **Per-pack tension:** resolved most cleanly of all four options, since per-pack SoC is untouched.
  The correction only ever applies to the bank aggregate, and only as a bias (or, if pushed further,
  distributed proportionally across packs' displayed SoC — but that requires deciding how to allocate a
  bank-level correction across packs with no way to observe which pack it belongs to, which reintroduces
  the bank-vs-per-pack tension one level down. Simplest correct version: correct the aggregate only,
  leave per-pack values as pure BMS passthrough, forever).
- **Honest downside:** most implementation complexity of the three real options — needs a dwell-time
  state machine, a resync-window Ah/SoC delta calculation, and a decision about correction magnitude
  limits (a bad shunt reading during the correction window could still nudge the aggregate wrong, just
  more slowly and less visibly than Option A, which is a mixed blessing — errors are gentler but also
  harder to notice/debug in the diagnostics page). It also means the aggregate's number will very
  occasionally not exactly equal the mean of displayed per-pack values anymore, which is a legibility
  cost the current implementation doesn't have (`soc_avg` today is exactly `mean(pack.soc)`, verifiably
  so; after correction it would not be, and someone doing mental math while looking at the dashboard
  would notice and could reasonably ask why).

## 4. Per-pack vs. bank-level tension, addressed directly

The dashboard today shows per-pack SoC (BMS, `pack{N}/soc`, `docs/mqtt.md:149`) and one aggregate
(`soc_avg`, BMS mean, `docs/mqtt.md:104`, `{base}/soc`, `docs/mqtt.md:62`). The shunt can only ever
speak to the aggregate — it has no way to distinguish packs. This is a hard physical constraint, not a
software limitation, so every option above has to answer the same question: **what does "the" SoC number
on the dashboard mean once a shunt exists, and does the user need to know which source it came from?**

- **Option A/B** (any variant that swaps or blends the *displayed* aggregate based on source): per-pack
  SoC stays pure BMS as today (it has no other choice), but the bank aggregate becomes a mix of two
  physically different measurements (mean-of-per-pack vs. whole-bank-integrated) depending on current
  level. This is the most confusing outcome for a user who tries to reconcile "why doesn't the big
  number match the average of the small numbers" — and with A/B, sometimes it will and sometimes it
  won't, with no visible reason why.
- **Option C**: cleanest separation — per-pack SoC (BMS) becomes explicitly informational/diagnostic
  only, and "SoC (shunt)" becomes the one primary number whenever available, with a persistent, honest
  UI label ("Source: SmartShunt" — already the exact wording `docs/ROADMAP.md:295` proposes for the
  current-value badge, so there's already a UI precedent to reuse) rather than a silently-changing
  value. The mismatch between the two is real and disclosed, not hidden — the user can look at
  "aggregate BMS mean: 44%" and "shunt: 42%" side by side and understand there are two independent
  measurements, rather than one number that mysteriously changes basis.
- **Option D**: per-pack values stay BMS-only and meaningful (they're never touched), and the single
  aggregate is always "the" bank SoC by construction — no second number to reconcile, because the shunt
  never surfaces as an independent displayed value, only as a correction input. This is the option that
  most avoids the "two numbers, which one is real" confusion, at the cost of the aggregate's provenance
  being slightly opaque (it's "mostly BMS, occasionally nudged" rather than being cleanly either "BMS
  mean" or "shunt reading").

Across all options, one thing is worth deciding explicitly regardless of which fusion strategy wins:
**the per-pack `pack{N}/soc` values should stay BMS-only in every option** — the shunt has no basis to
ever inform them, so there is no version of this feature where the shunt "overrides individual pack
SoCs." The only question in play is what happens to the single bank-level number.

## 5. Recommendation

**Recommend Option C (shunt-primary-when-online, BMS fallback), conditional on an empirical accuracy
check, with Option D as the fallback design if that check fails.**

Reasoning:

- Section 2 shows the hard-cutover and blend options (A, B) both have a real, likely-frequent failure
  mode (dithering near the threshold/band), not just a theoretical edge case — this rules them out as
  the primary design regardless of implementation cost. Building A first "to compare" is not needed
  since the failure mode is derivable from the current-fusion behavior already shipped, not something
  that requires a prototype to discover.
- Between C and D: C is architecturally simpler (no dwell-time state machine, no correction-magnitude
  limits to tune, no aggregate/per-pack-mean divergence to explain) and matches the *existing* stated
  direction in `docs/ROADMAP.md:285` ("BMS role shrinks to cell voltages + temps + alarms only" once a
  shunt exists) — this is not a novel direction for this project, it's already the plan on paper, just
  not reconciled with the more conservative "never override" comment currently sitting in the code
  (`source.h:28`). Recommend resolving that contradiction in favor of ROADMAP.md's intent for the
  *bank-level* number specifically, while keeping `source.h`'s "never override" language correct and
  scoped to *per-pack* SoC, which the shunt genuinely can never inform.
- The one real risk with C is the accuracy assumption at high current, which is a hardware claim this
  research can't verify without the BLE integration in hand. This should be a gated decision: ship the
  BLE plumbing and a diagnostics-only side-by-side log of shunt SoC vs. BMS `soc_avg` first (small,
  hardware-verifiable, matches the project's stated preference for incremental steps), confirm they
  track closely across at least one full charge/discharge cycle at varying current, *then* promote
  shunt to primary display. If they don't track well, fall back to Option D rather than force Option C
  through — D degrades gracefully to "BMS as always, shunt as a quiet corrective input" without ever
  needing to trust the shunt's absolute accuracy at high current, only its *relative* accuracy over
  short low-current windows, which is a much weaker and safer assumption.

**Needs owner input before implementation:**

1. **Resolve the `source.h:28` vs. `ROADMAP.md:290-292` contradiction explicitly.** Confirm: is the
   intended behavior "shunt SoC may become the primary *bank-level* display value" (ROADMAP.md), with
   "never overrides BMS SOC" in `source.h` reinterpreted as "never overrides *per-pack* BMS SOC"
   specifically? This research assumes yes; if not, Option C is off the table and D is the
   recommendation outright.
2. **Is `Config::SocMode {Calculated, RawBms, Hybrid}`** (`src/storage/config.h:95-96`, currently
   dormant) the intended config surface for this, analogous to `Config::ShuntCurrentMode`
   (`config.h:261-266`)? If so its three values need mapping onto whichever option is chosen (e.g.
   `RawBms` = never use shunt for the aggregate, `Hybrid` = Option D's correction model, and a
   currently-missing fourth "shunt primary" state would need adding for Option C — worth deciding
   whether to extend this enum or introduce a separate one).
3. **Does the owner want the empirical accuracy-check step as a hard gate** before shipping shunt as
   primary, or is Victron's shunt accuracy trusted enough from prior experience to skip straight to
   Option C? This affects whether V3.2 ships in one step or two (BLE + diagnostics-only comparison,
   then a follow-up PR promoting shunt to primary display).
4. **UI wording for the fallback/offline case in Option C** — `docs/ROADMAP.md:307`'s open question
   ("alert or silent fallback if shunt goes offline") is still open and applies directly here: a bank
   SoC that silently swaps basis from shunt to BMS mean on BLE disconnect has exactly the same
   discontinuity risk as section 2 describes, just triggered by a connectivity event instead of a
   current threshold. This needs the same "don't hide the jump" treatment — show a source badge and,
   if a jump is unavoidable at reconnect/disconnect, disclose it rather than smooth it away invisibly.
