# V3.2 — 6-pack hang investigation (unreachable every 24–48 h, no coredump)

**Status: investigation complete, no firmware change made.** No unbounded
pack-count-scaling resource was found in any recently-added code path. The
strongest evidenced candidate for the reported symptom is a **pack-count-
independent defect**: WiFi reconnect gives up permanently after 5 consecutive
failures (`StaFailed`), with no recovery path until power-cycle — which
reproduces the exact reported symptom (unreachable, no reboot, no coredump,
power-cycle required). Confirmation steps for the affected user are listed at
the end. Per the investigate-first mandate, no fix was applied without user-side
confirmation.

Report reference points:
- Owner (healthy): 3 packs, `3.2.0-rc.4`, DRAM largest block 31.0 KB @ 4 d 20 h,
  cycle ~594 ms avg / 1075 ms max.
- Affected user: 6 packs, `3.2.0-rc.2`, DRAM largest block 68.0 KB @ 20 h 43 m
  (snapshot shortly after a restart — shows nothing abnormal).

---

## 1. rc.2 → rc.4 delta: ruled out

`v3.2.0-rc.3` and `rc.4` are **not tagged/released**; they are the two commits
on the unmerged `fix/drift-cell-tag-overlap` branch (`16c4aa2`, `97182d1`).
Their entire content is `web/ui/app.js` + `web/ui/style.css` (drift "fills
first" tag layout) plus the `FW_VERSION` bump in `platformio.ini`.

**Conclusion: the owner's rc.4 firmware is byte-identical to the user's rc.2 in
every non-web-UI respect.** The version difference cannot explain the hang, and
upgrading the user to rc.4 would change nothing. The real variable between the
two systems is pack count (6 vs 3) and site environment (power, WiFi, cabling).

## 2. Pack-scaling code path audit — all bounded

Every recently-added per-pack path was audited for unbounded growth, leaks, or
pack-proportional lock/starvation behaviour:

| Path | Verdict | Evidence |
|---|---|---|
| RS485 poller / per-pack diag table | **Bounded** | `PollerStats.pack[16]` fixed counters (poller.h:47-52); stats copied under a µs-scale `portMUX` critical section; zero heap use in the poll loop (`rx_buf[256]` stack, `SysparamCache[16]` static) |
| Direction-aware safety lockout | **Bounded** | `runSafety()` is a pure function: no allocation, no locks, no I/O; single O(n) loop over ≤16 packs; `events[MAX_EVENTS]` overflow-guarded; lockout logic (runSafety.cpp:442-520) adds only two booleans + fixed flag writes |
| Drift / per-cell history | **Bounded** | `drift_ring` uses fixed `EXT_RAM_BSS_ATTR` PSRAM arrays sized `DRIFT_MAX_PACKS × DRIFT_MAX_CELLS` regardless of configured count (~22.8 KB total); file I/O once per UTC day |
| Sysparam per-pack fields | **Bounded** | `SysparamCache s_sysparam_cache[16]` fixed struct, overwritten in place (poller.cpp:39-48); no log/history semantics |
| MQTT publishing | **Bounded** | All publishes QoS 0 (no esp-mqtt outbox growth); `q_mqtt_publish` fixed 520-deep PSRAM queue with drop-oldest producer (housekeeping.cpp:73-82) and drain-while-disconnected consumer; per-pack/per-cell topics rotate via cursors — per-tick post count is constant, only rotation period grows with pack count |
| HA discovery burst | **Bounded** | worst-case 16-pack burst = 514 items < 520 queue depth; 6 packs ≈ 214 |
| Notify / alert debounce | **Bounded** | 32-slot static pending table with per-(type,pack) dedup (the June 2026 crash-loop fix); Telegram sends rate-limited ≥60 s and serialized by semaphore; per-send 16 KB task stack is transient with graceful alloc-failure handling |
| Alerts store | **Bounded** | fixed PSRAM ring, `persist()` dirty-gated at 5-min cadence |
| CAN TX | **Bounded** | bank-level frames from `SafetyState` (no per-pack loop), `twai_transmit` 10 ms timeout |
| Snapshot bus | **Bounded / lock-free** | double buffer + seqlock, reader bails after 10 retries |

### Cycle timing at 6 packs (analytical — no hardware available this session)

~198 ms per healthy pack (from owner's 594 ms @ 3) → **~1.2–1.4 s avg cycle at
6 packs**, well inside the 3 s poll period. Worst case with all packs offline:
6 × 500 ms + 500 ms RR ≈ 3.5 s — cycles then run back-to-back, but every wait is
a blocking UART read (yields to idle), so no watchdog/starvation risk. One
side-effect worth knowing: CAN TX runs on the same task *after* the poll cycle,
so the max inter-frame gap grows to ≈ cycle length (~1.4 s healthy, up to ~3.5 s
with offline packs) — could annoy a strict inverter, cannot hang the gateway.
**Get the user's `Cycle avg`/`Cycle max` from Diagnostics**: proportional
(~1.2 s / ~2.1 s) is expected; disproportionate values would point at bus
problems (collisions/late replies also visible as `wrong_addr`).

## 3. Watchdog / coredump analysis — why "no coredump" is informative

Config (sdkconfig.esp32s3): `TASK_WDT_TIMEOUT_S=60` + `TASK_WDT_PANIC=y`
(watching both idle tasks), `INT_WDT_TIMEOUT_MS=300`, panic handler → coredump
to flash (ELF + CRC), `COREDUMP_CHECK_BOOT=y`.

- Task-WDT, Int-WDT, panic, stack-overflow canary → **all would write a
  coredump and reboot**. No coredump + no self-reboot ⇒ none of these fired.
- Brownout reset → reboots **without** a coredump (by design), but the device
  would come back up — unless the supply stays degraded.
- **Diagnostic gap 1:** no application task is ever subscribed to the task WDT
  (zero `esp_task_wdt_add()` calls). Only the idle tasks are watched. A
  deadlocked ControlTask/MqttTask/httpd leaves idle running → no WDT, no dump,
  silent partial hang. Consider subscribing ControlTask (and optionally httpd)
  to the TWDT as a follow-up hardening item.
- **Diagnostic gap 2:** a power-cycle destroys `esp_reset_reason()` evidence.
  The persisted alert ring (LittleFS, 5-min flush) survives, though — see
  confirmation steps.

A full-device hang (both cores) with no dump is only reachable via hardware
(brownout/latch-up) — firmware deadlock would leave other tasks running. Since
the symptom is "unreachable", the network path is implicated, not ControlTask
(a ControlTask hang would leave the web UI reachable with stale data; the user
should be asked whether CAN/inverter data also stops during the failure —
this cleanly splits full-hang vs network-only-hang).

## 4. Strongest finding: WiFi `StaFailed` is a permanent dead end

`src/net/wifi.cpp` (event handler, lines 83–168):

- Post-connection disconnect → mode `StaConnecting`, `g_retry = 0`, reconnect.
- Every further failure increments `g_retry`; after `MAX_RETRY = 5`
  (wifi.cpp:28) → `g_mode = StaFailed` and — verbatim comment — *"If g_mode is
  StaFailed / ApActive / Off we have nothing useful to do."*
- **Nothing ever leaves `StaFailed` at runtime.** The captive-portal fallback
  runs only in the boot path (boot.cpp is the only `is_connected()` consumer);
  self-test/OTA-rollback is boot-only; no periodic retry task exists.

With `WIFI_ALL_CHANNEL_SCAN`, 5–6 attempts burn in roughly **15–30 seconds**.
Any AP outage longer than that (router reboot 1–3 min, mesh node restart,
firmware update, band-steering kick, DHCP hiccup, momentary heavy RF
interference) leaves the gateway **permanently offline: web + MQTT dead, RS485
polling and CAN TX still running, no reboot, no watchdog, no coredump —
recoverable only by power-cycle.** This is an exact match for the report.

It is *not* pack-count-scaling and *not* new in rc.2 (`MAX_RETRY=5` predates
Phase H3c) — which is consistent with the owner never seeing it: his AP simply
never disappears for >30 s. A 24–48 h recurrence fits a site with a nightly
router reconnect/reboot or unstable mesh.

Deliberately **not patched** in this branch: the defect is proven by code
inspection, but whether it is what this user hits is not yet confirmed
(investigate-first mandate). The fix, once confirmed, is small and touches no
safety code: retry forever with backoff after a post-connection loss (e.g. keep
calling `esp_wifi_connect()` on a 10–30 s timer while in `StaFailed`), plus an
alert on entry/exit.

## 5. Soak test — not feasible this session

No ESP32-S3 on USB (`/dev/cu.*` shows none) and the Raspberry Pi simulator host
(`bms-pi`, 192.168.178.133) is unreachable from this machine. In place of a
soak, every steady-state allocation path was audited (section 2): the firmware's
hot paths are allocation-free by design (static PSRAM buffers, fixed queues,
fixed rings), so there is no per-cycle heap churn that could compound at 6 packs.
Remaining fragmentation sources (notify 16 KB transient task stacks, esp-mqtt
reconnects, httpd sessions) are load-dependent but bounded and fail gracefully.
A ≥24 h 6-pack soak against the Pi simulator tracking `dram_free` /
`dram_largest_block` / per-task stack HWM (all already exposed in `/api/diag`)
is still the right follow-up when the hardware is available.

## 6. Side finding (unrelated to hang, worth fixing separately)

The host safety test suite (`test/host`, ctest) has **14–16 pre-existing
failures** in the `[factor]/[edge]/[soc]/[proto]` groups — verified identical
before and after the direction-aware-lockout commit (3630bc3 even notes
"pre-existing [soc]/[factor] golden failures unchanged"). CI only runs
`pio test -e native` (a smoke test), so the real safety suite is not gated.
The failures look like stale test expectations from the Auto-mode-default
config change (tests assume Manual-mode `count × charge_amps` behaviour), not a
firmware bug — but a safety-critical module with a permanently red, un-gated
test suite is a hygiene problem: regressions in `runSafety()` would currently
ship invisibly.

## 7. Hypotheses, ranked

1. **WiFi permanent `StaFailed` wedge (confidence: high that the defect exists,
   medium-high that it is this user's root cause).** Exact symptom match;
   pack-count-independent, environment-dependent — explains 6-pack user vs
   3-pack owner without any pack-scaling mechanism.
2. **Site power / brownout (confidence: low-medium).** 6-pack installations
   often power the gateway differently; brownout reset leaves no coredump. But
   the device should recover after a brownout reset unless the rail stays low;
   ask about the gateway's supply.
3. **Slow DRAM exhaustion/fragmentation under 2× load (confidence: low).**
   Audit found no unbounded path; both reference snapshots look healthy. Note:
   momentary DRAM pressure that makes 5 consecutive WiFi reconnects fail would
   *convert into* hypothesis 1's permanent wedge — the retry cap amplifies any
   transient trouble into a power-cycle event.
4. **Deadlock/starvation scaling with pack count (confidence: very low).** All
   critical sections are short, non-nested spinlocks; no lock is held across
   the per-pack loops; all blocking waits have timeouts. A ControlTask hang
   would also leave the web UI reachable, contradicting the symptom.
