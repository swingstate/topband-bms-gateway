# V3.2 — Pylontech CAN conformance audit (proactive, full frame set)

Status: **audit complete, no encoder change required.** Reference decoder:
OpenDTU-onBattery `src/battery/pylontech/Provider.cpp` (the parser Deye/OpenDTU
users actually run — the same source that found the 0x35C bit-swap and the false
under-temperature bug). Verified verbatim against the parser's byte offsets, bit
numbers (`getBit` is LSB0), scale factors and sign handling.

## Method

Not reasoning from memory. Each frame `can::pylontech::build_*()` was compared
field-by-field against the corresponding `readSignedInt16` / `readUnsignedInt16` /
`getBit` call in the OpenDTU Pylontech provider.

**Every alarm/protection bit in 0x359 is on its correct byte and bit.** No
misplaced bit, no severity encoded on the wrong slot.

### Cell drift / imbalance
The standard Pylontech 0x359 defines **no** cell-imbalance / drift bit (OpenDTU
has none; the Topband datasheet defines none either). The gateway correctly does
NOT invent one — `alarm_flags 0x20` (drift) is surfaced via UI/MQTT only, never
mapped onto an unrelated 0x359 bit.

### 0x4200 / 0x7320
These are the Pylontech **SC0500 high-voltage console** protocol (EEVblog thread),
not part of the LV stack OpenDTU/Deye parse. Correctly not implemented.

### 0x355 byte 4-5 deviation (flagged, NOT changed)
The code writes `capacity_total_ah × 10` into 0x355 bytes 4-5 in **all three**
protocol builders (Victron/SMA/Pylontech) — V2.67 legacy. OpenDTU's Pylontech
parser reads only bytes 0-3, so those bytes are ignored by the reference decoder
and by Deye. Left unchanged because: (a) it causes no wrong behaviour on the
reference/Deye path, (b) it is a cross-protocol legacy layout, not a Pylontech
bug, and (c) changing a shipping CAN byte layout is gated by CLAUDE.md and could
affect an inverter that DOES display capacity from it. Recorded here for a future
strict-conformance pass with owner sign-off.

## The Deye "Lithium Mode stops discharging" symptom — explained WITHOUT an encoder bug

Root cause is the gateway's own **over-voltage lock-to-zero**, correctly encoded:

1. The gateway's hard cell OVP ceiling is `LIFEPO4_CELL_MAX_V = 3.65 V`
   (`safe_cell_volt` default 3.55 V, capped at 3.65 V). The owner's cell briefly
   hit **3.700 V** — above the ceiling.
2. `runSafety()` sets `alarm_flags 0x02` (over-voltage) when
   `cell_max_v > eff_cell_cap_v` (runSafety.cpp:241).
3. The **lock-to-zero rule** (runSafety.cpp:442-448) zeroes BOTH `safe_chg` AND
   `safe_dis` on `0x02`. So the gateway itself disables discharge.
4. That propagates faithfully to all three frames: 0x351 DCL = 0, 0x35C
   discharge-enable = 0 (dcl < 0.1), and 0x359 byte0 bit1 over-voltage = 1.

So a Deye in Lithium Mode stops discharging because **the gateway told it to**
(DCL 0 + discharge-enable No), not because of any bit-mapping error. Even an
inverter that ignored 0x359 alarms entirely would still stop, because DCL is 0
in 0x351 and discharge-enable is No in 0x35C.

### Alarm-severity vs protection-severity — does it matter?
The gateway has a **single** over-voltage threshold (3.65 V) which it treats as
protection (it locks charge AND discharge to zero). It has no separate
"warning-only" over-voltage level. Therefore encoding the condition as a 0x359
**protection** bit is internally consistent with what the gateway actually does —
it is not a warning masquerading as a protection. There is no severity-mapping
bug. On the inverter side, Deye's Lithium Mode does treat any alarm bit as a
discharge inhibitor, but that never gets exercised in isolation here because the
current-limit path (0x351 DCL / 0x35C discharge-enable) already stops discharge.

### Owner takeaway (control-logic observation, out of scope for this display-only task)
Whether over-voltage *should* also lock discharge (vs. only charge) is a
control-logic question. Discharging an over-voltage pack is arguably the correct
recovery. Changing that is a safety-control change (forbidden by this task's
invariants) and needs its own owner-approved decision — noted, not changed here.
The 3.700 V event is now fully traceable on the Diagnostics page (CAN section
shows the active over-voltage alarm, DCL 0, discharge-enable No; Battery/BMS
table shows which pack/cell exceeded 3.65 V).
